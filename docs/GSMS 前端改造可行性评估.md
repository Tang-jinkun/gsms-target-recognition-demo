# GSMS 前端改造可行性评估

> 评估对象：`docs/` 下四份新版设计文档
> - GSMS 智能工作台页面说明
> - GSMS 数据管理页面说明
> - GSMS Skills 管理页面说明
> - GSMS 设置页面说明
>
> 评估基线：当前仓库 `frontend/`（单页 `/workbench`）与 `backend/`（FastAPI assets + models + jobs）。
> 评估日期：2026-06-02。

---

## 0. 评估结论速览（TL;DR）

**一句话结论：纯前端页面层面，四个页面几乎全部可行（中低风险）；但这套设计的真正核心——"Agent 自动调用 InVEST"——本质上不是一次前端改造，而是一个需要从零新建的"后端 + Agent 运行时 + LLM 网关"工程。可行，但请按"它是一个新后端项目"来排期，而不是"给现有前端加几个页面"。**

| 模块 | 前端可行性 | 后端依赖 | 综合风险 |
|---|---|---|---|
| 顶部导航 + 多页 AppShell | 🟢 高 | 无 | 🟢 低 |
| 数据管理（目录树→文件→元数据） | 🟢 高 | 🟡 需新增"目录/文件夹"模型 | 🟡 中 |
| 设置（用户信息 + 模型配置） | 🟢 高 | 🔴 需新增凭据存储 + 连通性测试 | 🔴 中高（安全） |
| Skills 管理（列表 + 文件树 + 内容渲染） | 🟢 高 | 🟡 需新增 Skills 存储 + 文件读取 API | 🟡 中 |
| 智能工作台 - 手动运行（弹窗 + Map/图层/日志） | 🟢 高（大量复用现有代码） | 🟢 已具备 | 🟢 低 |
| 智能工作台 - **Agent 自动调用** | 🟡 UI 可行 | 🔴 **整套 Agent 运行时与编排不存在** | 🔴 **高** |

**瓶颈不在前端，在后端与 Agent。** 把这一点错判为"前端任务"是本次改造最大的排期风险。

## 1. 变化的本质：一次产品转向，而非增量迭代

### 1.1 形态变化

| 维度 | 现状 | 新设计 |
|---|---|---|
| 页面数 | 1（`/workbench`） | 4（工作台 / 数据管理 / Skills / 设置）+ 顶部导航 |
| 主交互入口 | 右栏 schema 表单手动跑 Carbon | **中央 Agent 对话框，自动跑模型** |
| 模型调用 | 用户填表单 → Run | Agent 自动选模型/配数据/配参数/直接运行 |
| LLM | 无 | 多供应商对话模型配置 + 选择器（核心依赖） |
| 用户/凭据 | 无 | 用户信息 + 各家 API Key |
| 数据组织 | 扁平 asset 列表，单 `default` project | 目录树 / 文件夹 / 项目 |
| Skills | 无 | 本地 Skills 文件浏览 |

### 1.2 ⚠️ 与既有"设计红线"的直接冲突（需先决策）

当前仓库内**权威文档**明确把 Agent 与用户系统排在 MVP 之后，新设计直接推翻了这些约定，必须先在团队层面对齐，否则两套文档会长期打架：

- `invest-webgis-workbench-development-plan.md` §19 / §4.2：第一版**不做** agent 自动运行、不做用户系统、单 default project。
- `frontend-design.md` §16 红线：**不做登录注册、不做 agent 自动决策**；§15 Phase E 还规定"agent 只辅助、用户仍能看到并修改所有显式参数、**agent 生成的操作必须可审计**"。
- 新设计 §22 则要求 Agent 自动调用时**不弹配置窗、不要求用户确认、不要求逐项填参、直接运行模型**。

> **这不是一个可以"两边都满足"的细节，而是产品方向的取舍。**
> **已决策（2026-06-02）**：新设计**正式取代**旧 MVP 红线（详见 §7.2 第 1 项）。旧文档需补注"已被 GSMS 新设计取代"。Agent 自动运行仍保留运行前确认，且当前阶段只做到纯聊天（§4.2、§7.2 第 2 项）。

## 2. 现状基线：可复用资产清单

改造并非从零，以下现有能力可直接复用，显著降低前端工作量：

**前端（`frontend/src`）**
- 三栏布局骨架、Tailwind/shadcn 风格、`ui/Button`、`ui/Input`、新抽出的 `ui/Tabs(SegmentedTabs)`、`lib/format`。
- `MapCanvas.tsx`：MapLibre 初始化、图层增删、raster/geojson 渲染、要素属性、坐标/缩放 —— **可几乎原样搬到新工作台的 Map 视图**。
- 图层与资产状态：`stores/useStores.tsx` 的 `useLayersStore` / `useAssetsStore`。
- **schema 驱动表单**：刚重构出的 `components/right/RunTab.tsx` + `ModelForm.tsx` + `types.ts` —— **正好可改造成新设计 §24 的"手动模型配置弹窗"**。
- 任务状态/日志/输出：`components/right/ResultsTab.tsx` —— **正好对应新设计 §18 "右侧轻量状态 + 日志"**。

**后端（`backend/app/main.py`，678 行）**
- `GET /api/models`、`/api/models/{id}/schema`、`/api/models/{id}/check-inputs`：Agent 选模型、校验输入时可直接当作工具调用。
- `POST /api/jobs` + 日志/输出/预览一整套：Agent 自动运行 = 复用这条链路。
- assets 上传/列表/元数据/preview：数据管理页与附件功能的基础。

**结论：工作台的"地图 + 图层 + 手动运行 + 日志"部分复用率很高；新增成本集中在 Agent、LLM、Skills、目录树、设置/凭据这些"现仓库完全没有"的能力上。**

## 3. 逐页可行性评估

### 3.1 顶部导航 + 多页 AppShell —— 🟢 低风险

- **新需求**：顶部系统导航（工作台/数据管理/Skills/设置/用户），各页选中态；三栏/两栏主体随页面不同。
- **现状差距**：当前只有 `/workbench` 与占位 `/index`，`Layout.tsx` 是工作台专用、没有导航、没有路由壳。
- **前端可行性**：高。Next.js Pages Router 直接加 `pages/data.tsx`、`pages/skills.tsx`、`pages/settings.tsx`；把 `Layout.tsx` 拆为 `AppShell`(TopNav + `StoresProvider`) + 各页 body；`_app.tsx` 包裹全局。
- **后端依赖**：无。
- **风险**：低。唯一要注意的是**全局状态作用域**——现在 `StoresProvider` 只包工作台，跨页共享（如当前项目、已配置模型）需要提升 Provider 层级。

### 3.2 数据管理 / Data Hub —— 🟢 前端高 / 🟡 后端中

- **新需求**：目录树 → 文件列表（名/类型/大小）→ 文件元数据（含空间元数据 CRS/几何/范围/分辨率/波段）；上传、新建文件夹、导入、搜索。
- **现状差距**：后端是**扁平** asset 列表，路径写死 `data/projects/default/assets`，**没有"文件夹/目录树"概念**，没有"新建文件夹/移动"。元数据读取已具备（`read_asset_metadata`）。
- **前端可行性**：高（标准三栏文件浏览器，元数据右栏可复用工作台 `MetadataDetails` 逻辑）。
- **后端依赖**：🟡 需要新增——目录树 API、按目录列文件、新建文件夹、（可选）导入；要决定是否引入真正的 project/folder 数据模型（建议同时落地 SQLite，开发计划早已规划但未做）。
- **风险**：中。主要是后端数据模型从"扁平"升级为"层级"的迁移成本。

### 3.3 设置 / Settings —— 🟢 前端高 / 🔴 后端中高（安全）

- **新需求**：用户信息；**对话模型配置**（名称/供应商/API Key/Base URL/模型 ID/默认/连接状态）；添加/编辑/删除、**测试连接**、默认模型；工作台选择器读取此处配置。
- **现状差距**：**后端完全没有**用户、没有模型供应商配置、没有凭据存储、没有连通性测试。前端 Top Bar 现有一个 `Settings` 占位按钮（无功能）。
- **前端可行性**：高（左菜单 + 右表单 + 列表，标准 CRUD）。
- **后端依赖**：🔴 必须新增——
  - 凭据**安全存储**（至少静态加密，**绝不**回传明文 Key 给前端，**绝不**写日志）。
  - `POST /api/llm-providers/{id}/test`：用最小请求探测各家 API 可用性。
  - 这是后续 Agent 的**前置依赖**：Agent 没有可用模型就无法工作。
- **风险**：中高，集中在**密钥安全**与**多供应商兼容**（OpenAI/Anthropic/DeepSeek/Qwen/Local/Custom 各有鉴权与 Base URL 差异）。

### 3.4 Skills 管理 —— 🟢 前端高 / 🟡 后端中

- **新需求**：两层——列表（名/一句话描述/更新时间/搜索/导入）→ 详情（面包屑 + 文件树 + 文件内容：md 渲染 / 代码只读 / 文本只读 / 二进制提示不可预览；默认选中 SKILL.md→README.md→空态）。
- **现状差距**：后端**没有 Skills 存储与读取 API**；前端无 Markdown 渲染、无代码高亮、无文件树组件。
- **前端可行性**：高，但需引入依赖：Markdown 渲染（如 `react-markdown`）、（可选）代码高亮、文件树组件。
- **后端依赖**：🟡 需要——Skills 列表、Skill 文件树、文件内容读取（注意**路径穿越**防护：限制在 skills 根目录内）。
- **风险**：中。功能定位克制（只读浏览，不测试/不安装依赖），范围可控。

### 3.5 智能工作台 —— 拆成两条独立可行性

工作台是改造重心，必须把它**拆成两块分别评估**，因为可行性天差地别。

#### (A) 手动运行 + 地图 + 图层 + 日志 —— 🟢 低风险

- **新需求**：左栏 图层/文件/InVEST 三 Tab；中央 Map 视图；右栏轻量"任务状态 + 日志"；手动调用走**模型配置弹窗**（§24）。
- **现状差距**：小。当前右栏的 schema 表单要从"常驻面板"迁移为"弹窗"；右栏改为只剩 ResultsTab 的状态+日志；左栏增加 InVEST Tab。
- **可行性**：高，**大量复用**第 2 节列出的现有组件。这是最稳的部分，可以最先落地。

#### (B) Agent 自动调用 InVEST —— 🔴 高风险（真正的难点）

- **新需求**（§22）：用户自然语言 → Agent 理解 → **自动选模型 / 自动匹配数据 / 自动生成参数 / 直接运行 / 结果回流地图与对话**，全程不确认。
- **现状差距**：**整套能力为零**。需要新建：
  1. **Agent 运行时**：一个 LLM 工具调用（tool-use）循环，把现有 `/api/models`、`check-inputs`、`/api/jobs` 包装成工具，让模型按需调用。
  2. **数据匹配/参数生成逻辑**：把项目里的栅格/表格自动映射到模型 `ModelInputSpec`（如 LULC raster、carbon pools CSV）。这是**语义匹配**，错配会直接导致科学结果错误。
  3. **对话持久化**：会话历史、附件、流式输出（SSE/WebSocket）。
  4. **LLM 网关**（依赖 3.3 设置页）。
- **前端可行性**：聊天 UI 本身可行（输入卡片、附件标签、模型选择器、消息流、Agent/Map/Split 视图切换）。
- **风险**：🔴 高，详见第 4 章。

## 4. 横切关键依赖与风险（决定整体可行性）

### 4.1 Agent 运行时是一个独立工程，不是前端组件
"Agent 自动选模型并运行"需要：tool-use 编排、把后端能力暴露为工具 schema、错误恢复、流式回传、可观测性。这是后端/AI 工作量的**大头**，且 InVEST 任务是**长任务**（现有 job runner 是 subprocess + 轮询），Agent 还要异步等待并把结果接回对话。**建议把它当成与现有 MVP 同级的独立里程碑来排期。**

### 4.2 "自动运行、不确认"对科学正确性是真实风险
设计要求 Agent **不经确认直接运行**模型。但：
- 数据自动匹配可能选错输入（如把错误年份的 LULC 当 baseline），用户**无法在运行前发现**；
- InVEST 跑一次有真实计算成本，错配 = 浪费 + 误导性结果；
- 这与既有红线"agent 操作必须可审计、用户能看到并修改参数"直接矛盾（§1.2）。

> **已决策（2026-06-02）**：运行前确认**确定要做**——在"直接运行"前插入一个**轻量可跳过的确认卡片**（展示选中的模型 + 匹配到的数据 + 关键参数，一键确认/修改）。但**当前前端阶段只做到"纯聊天"**：Agent 视图先交付聊天 UI 外壳，tool-use 编排与确认卡片随 Phase 5b 落地（见 §6）。

### 4.3 后端数据模型缺口集中爆发
新设计同时引入 **scene（工作台外层场景）、project/folder（数据管理）、skills、user、llm-provider、chat** 六类新实体，而后端现在连 SQLite 都没有（asset 靠扫目录）。其中 **scene 还要求工作台内的 assets/jobs/chat/图层都按 `sceneId` 隔离**，是一条横切约束。**强烈建议**在动这些页面前先落地一个最小持久化层（开发计划 §7 早已规划 SQLite），否则各页面各写一套临时存储会迅速失控。

### 4.4 密钥安全是设置页的硬要求
多供应商 API Key 必须：服务端存储、静态加密、**不回传明文、不进日志、不进前端 bundle**。测试连接在服务端发起。这是合规/安全红线，不能用前端 localStorage 糊弄。

### 4.5 前端两项前置改造（Enabler）
新增四页 + 跨页共享状态（当前项目、已配置模型、运行中任务）会让现有问题恶化，建议**先做、否则后面返工**：
- **AppShell 化**：拆 `Layout.tsx` → `AppShell(TopNav)` + 各页 body；Provider 提升到 `_app`。
- **状态层与 apiClient**：现有单一 God-Context（`useStores.tsx` 706 行，无 `useMemo`，每秒轮询触发全树重渲染）已是债务；再叠 chat/settings/skills 会更糟。建议借机引入 `lib/apiClient` + 按域拆 store（Zustand/Jotai，开发计划本就推荐）。详见上一轮架构批判。

## 6. 分阶段可行路线（建议）

按"低风险先行、Agent 压轴、先修使能项"排序。工作量为粗量级（T-shirt：S≈数天，M≈1-2 周，L≈2-4 周，XL≈1 月以上，且 XL 多为后端/AI）。

- **Phase 0 — 使能改造（S–M）**：AppShell + TopNav + 多路由；提升 Provider；（强烈建议）`apiClient` + store 拆分。无新后端。
- **Phase 1 — 工作台手动闭环重排（M）**：左栏三 Tab、Map 视图、右栏轻量状态+日志、手动运行弹窗。**全部复用现有代码，最稳，建议最先交付可演示版本。**
- **Phase 2 — 数据管理（M）+ 后端目录模型（M）**：目录树/文件列表/元数据；后端引入 folder + 建议 SQLite。
- **Phase 3 — 设置页 + LLM 网关（L，含安全）**：模型配置 CRUD、凭据安全存储、测试连接。**这是 Agent 的前置依赖。**
- **Phase 4 — Skills 管理（M）**：列表 + 详情（文件树 + md/代码渲染）+ 后端 skills 读取 API。
- **Phase 5a — 纯聊天 UI（M，前端为主）【当前阶段目标】**：Agent 视图的聊天外壳——消息流、输入卡片、附件标签、对话模型选择器、Agent/Map/Split 视图切换、（最小）会话持久化。**此阶段不接 tool-use、不自动跑模型、不做确认卡片**，是一个能对话的前端壳。
- **Phase 5b — Agent 编排 + 运行前确认（XL，后端/AI 为主）【已承诺、暂不做】**：tool-use 编排 + 数据匹配/参数生成 + 调用现有 job runner + 流式回传 + **运行前确认卡片（已决策必做，见 §4.2）**。**改造的真正难点与不确定性集中于此。**

> 里程碑：Phase 0–1 完成即得"多页 + 可手动跑 InVEST"的可演示系统；Phase 3 完成才具备接入 Agent 的前提；Phase 5a 给出 Agent-first 的**交互外壳**；Phase 5b 才真正兑现"Agent 自动运行 + 运行前确认"的完整闭环。

## 7. 结论与待决策项

### 7.1 可行性结论
- **前端层面**：四个页面 + 工作台重排**整体可行、风险可控**，且现有地图/图层/表单/日志组件复用率高。
- **真正瓶颈**：设置页凭据安全、后端层级数据模型、尤其是 **Agent 自动调用运行时**——这些是**新建的后端/AI 工程**，决定整个改造的周期与成败。
- **总判断**：**可行，但请按"前端重排（数周）+ 一个新后端/Agent 项目（数月级，含不确定性）"两段来管理预期**；若误判为纯前端任务，排期必然失真。

### 7.2 决策结论（2026-06-02 已确认）
1. ✅ **方向冲突**：新 GSMS 设计**正式取代** `frontend-design.md` / 开发计划中"不做 agent 自动决策、不做用户系统"的红线。→ **行动项**：更新旧文档（或加注"已被 GSMS 新设计取代"），避免长期矛盾。
2. ✅ **Agent 运行前确认**：**确定要做**一个可跳过的"模型+数据+参数确认卡片"（§4.2）。**但当前前端阶段只做到"纯聊天"**——确认卡片随 Phase 5b 落地，Phase 5a 先交付聊天外壳。
3. ✅ **后端持久化**：落地 SQLite + project/folder 模型（§4.3）。
